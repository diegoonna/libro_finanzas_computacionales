4 Introducción

Hasta ahora hemos escrito código de forma lineal. Esta semana aprendemos a encapsular lógica en funciones reutilizables, siguiendo el principio DRY (Don’t Repeat Yourself). Al final, tendremos nuestra propia librería finanzas_basicas.py.

5 Definición de Funciones

Una función es un bloque de código reutilizable que recibe parámetros y devuelve un resultado.

5.1 Recibir y devolver múltiples valores

En Python, una función puede recibir varios parámetros y también devolver más de un resultado. Esto es útil en finanzas cuando, a partir de los mismos datos, queremos obtener más de un indicador.

Cuando devolvemos varios valores, Python los empaqueta en una tupla. Luego podemos “desempaquetarlos” en variables separadas para trabajar con cada resultado de forma clara.

5.2 Parámetros por Defecto

5.3 Argumentos Variables (*args)

Hasta ahora vimos funciones con una cantidad fija de parámetros.
Pero en problemas financieros muchas veces no sabemos de antemano cuántos valores vamos a procesar (por ejemplo, una serie de flujos que puede tener 3, 10 o 30 períodos).

*args permite que una función reciba una cantidad variable de argumentos posicionales. Dentro de la función, esos argumentos se agrupan en una tupla.

Esto nos da flexibilidad sin tener que escribir versiones distintas de la misma función.

Con esto:

  • sumar_flujos(100, 200, 300) envía 3 argumentos,
  • sumar_flujos(80, 80, 80, 80, 1080) envía 5,
  • y sumar_flujos(*serie) toma una lista y la transforma en argumentos separados.
TipCuándo usar *args

Usá *args cuando la función necesite aceptar una cantidad variable de datos del mismo tipo (flujos, retornos, precios, etc.).
Si cada dato tiene un rol distinto y fijo (por ejemplo capital, tasa, periodos), conviene usar parámetros explícitos.

6 Scope (Alcance) de las Variables

El scope o alcance define en qué parte del programa una variable es “visible” y puede ser utilizada. En Python, distinguimos principalmente entre dos niveles:

  1. Scope Global (Main): Variables definidas fuera de cualquier función. Son visibles en todo el archivo, incluso dentro de las funciones.
  2. Scope Local: Variables definidas dentro de una función. Solo existen mientras la función se está ejecutando y no pueden verse desde fuera.

6.1 Variables Globales vs. Locales

Una función puede leer una variable global, pero no puede modificarla directamente: para eso existe la declaración global tasa_mercado dentro de la función. Que exista no significa que convenga usarla — en código financiero es una mala práctica, porque una función que modifica estado externo se vuelve impredecible (el resultado deja de depender solo de sus parámetros). En todo este libro, las funciones reciben lo que necesitan por parámetro y devuelven resultados con return.

6.2 El concepto de “Shadowing” (Sombreado)

Si definimos una variable dentro de una función con el mismo nombre que una global, la versión local “sombra” a la global durante la ejecución de esa función.

6.3 ¿Por qué evitar las variables globales?

En el desarrollo de software financiero, la pureza de las funciones es fundamental. Una función ideal es aquella que, para los mismos parámetros, siempre devuelve el mismo resultado sin depender de “estados externos”.

ImportanteRegla de Oro

Siempre que necesites un dato dentro de una función, pásalo como parámetro. Evita depender de variables definidas en el “main” para que tu código sea modular y fácil de testear.

6.4 ¿Qué recibe una función cuando le pasás una lista?

Cerremos el círculo con el concepto de aliasing del Capítulo 2 (“copiar no es lo mismo que apuntar”), porque tiene una consecuencia directa sobre las funciones. Cuando llamás mi_funcion(cartera), la función no recibe una copia de la cartera: recibe otra etiqueta al mismo objeto. A las funciones que cumplen esto se las llama puras, y son las más fáciles de testear, reutilizar y razonar. Todas las funciones de la librería que construimos al final del capítulo son puras.

7 Manejo de Errores: try / except

En el mundo real, los datos financieros casi nunca llegan “perfectos”: pueden venir incompletos, en formato incorrecto o fuera de rango. El manejo de excepciones con try / except permite que el programa sea robusto, evitando que se rompa ante errores esperables.

7.1 ¿Qué es una excepción?

Una excepción es un error que ocurre durante la ejecución del programa (runtime), por ejemplo:

  • dividir por cero (ZeroDivisionError),
  • convertir texto a número cuando no se puede (ValueError),
  • acceder a una clave inexistente en un diccionario (KeyError),
  • o intentar usar un tipo de dato incorrecto (TypeError).

Si no capturamos la excepción, el programa se detiene e imprime un traceback — el “informe forense” del error. Saber leerlo es probablemente la habilidad que más tiempo te va a ahorrar en toda tu carrera, así que detengámonos un minuto.

TipCómo leer un traceback (la habilidad subvalorada)

Un traceback típico luce así:

Traceback (most recent call last):
  File "analisis.py", line 42, in <module>
    resultado = valuar_cartera(posiciones)
  File "analisis.py", line 17, in valuar_cartera
    total += valuacion_bono(bono, tasa)
  File "finanzas_basicas.py", line 8, in valuacion_bono
    return cupon / (1 + tasa) ** t
ZeroDivisionError: division by zero

La receta para leerlo:

  1. Empezá por la última línea: ahí está el tipo de error (ZeroDivisionError) y el mensaje (division by zero). Es el “qué pasó”.
  2. Subí una línea: es el lugar exacto donde explotó (finanzas_basicas.py, línea 8). Es el “dónde”.
  3. El resto, de abajo hacia arriba, es la cadena de llamadas: quién llamó a quién hasta llegar ahí. El “cómo llegamos”. Ojo: la línea que explotó no siempre es la culpable — acá el bug probablemente esté en quien pasó tasa = -1, no en la fórmula.

El error de principiante es leer solo la primera línea (que es la menos informativa) o, peor, no leer nada y adivinar. El traceback te está diciendo exactamente qué, dónde y cómo — gratis.

Con try / except, en cambio, podemos capturar el error y decidir cómo responder sin que el programa muera.

7.2 Flujo de try / except

La estructura general es:

try:
    # código que puede fallar
except TipoDeError:
    # qué hacer si ocurre ese error

La idea clave es separar:

  • camino normal (cálculo esperado),
  • de camino de error (qué hacemos cuando algo falla).

7.5 Uso de else y finally

Además de except, Python ofrece dos bloques muy útiles:

  • else: se ejecuta si no hubo excepción en try.
  • finally: se ejecuta siempre, haya error o no.

En análisis financiero real, finally suele usarse para cerrar archivos, conexiones o liberar recursos.

7.6 raise: generar errores de negocio explícitos

No solo capturamos errores: también podemos lanzarlos cuando una regla financiera no se cumple.

7.7 Buenas prácticas en try / except

  1. Capturar errores específicos (ValueError, TypeError, etc.), no usar except: genérico salvo casos muy controlados.
  2. Mantener el bloque try pequeño (solo las líneas que pueden fallar).
  3. Dar mensajes claros para quien usa el programa.
  4. Validar supuestos de negocio con raise (tasas, plazos, signos de flujos).
  5. No ocultar errores silenciosamente (pass) si eso dificulta detectar problemas.
ImportanteIdea clave

try / except no reemplaza una buena lógica: la complementa.
Primero validamos reglas financieras, luego capturamos errores inevitables del mundo real.

8 Módulos y librerías en Python

Cuando un programa crece, no conviene dejar todo en un solo archivo. Python permite organizar el código en módulos para reutilizar funciones, mantener orden y facilitar el testing.

8.1 ¿Para qué sirve un módulo?

Un módulo es, en la práctica, un archivo .py con funciones, variables o clases.

Nos sirve para:

  • separar responsabilidades (por ejemplo, valuación de bonos en un archivo y conversión de tasas en otro),
  • reutilizar lógica en distintos scripts o notebooks,
  • evitar duplicación de código (principio DRY),
  • y mejorar mantenimiento y legibilidad.

8.2 Diferencia entre módulo y librería

  • Módulo: un archivo Python individual, por ejemplo finanzas_basicas.py.
  • Librería: un conjunto de módulos relacionados que resuelven un dominio o problema.
    Ejemplos: numpy, pandas, matplotlib.

En cursos introductorios, a veces se dice “librería” para referirse a un solo archivo propio. Técnicamente, ese archivo es un módulo, aunque puede ser el primer paso para construir una librería más completa.

8.3 Formas de importar: import, from, as

NotaBuena práctica

En general, preferí import modulo o import modulo as alias porque hacen explícito de dónde viene cada función (modulo.funcion).
from modulo import * no se recomienda en producción porque puede sobrescribir nombres y volver ambiguo el código.

10 Principio DRY: Don’t Repeat Yourself

El principio DRY (Don’t Repeat Yourself) propone evitar duplicar la misma lógica en distintos lugares del código. Cuando repetimos fórmulas o bloques manualmente, aumentamos el riesgo de inconsistencias: si cambia un supuesto (por ejemplo, la tasa o la frecuencia), debemos corregir múltiples líneas y es fácil olvidar alguna.

Aplicar DRY en finanzas significa encapsular cálculos recurrentes en funciones (por ejemplo, valuacion_bono() o valor_presente_neto()) para tener:

  • menos errores de mantenimiento,
  • mayor claridad del modelo,
  • reutilización en distintos ejercicios o casos,
  • y validaciones centralizadas en un solo lugar.
TipDRY en la Práctica

Antes de copiar y pegar código, preguntate: ¿puedo hacer una función?

Sin DRY (malo):

precio_a = 80/(1.1) + 80/(1.1**2) + 1080/(1.1**3)
precio_b = 60/(1.08) + 60/(1.08**2) + 1060/(1.08**3)

Con DRY (bueno):

precio_a = valuacion_bono(1000, 0.08, 0.10, 3)
precio_b = valuacion_bono(1000, 0.06, 0.08, 3)

11 Errores comunes

AdvertenciaTrampas frecuentes
  • Argumento por defecto mutable: def agregar(flujo, lista=[]) comparte la MISMA lista entre todas las llamadas — los flujos de un bono aparecen en otro. El idioma correcto: def agregar(flujo, lista=None) y crear la lista adentro (if lista is None: lista = []).
  • Olvidar el return: una función que calcula pero no retorna devuelve None silenciosamente; el error explota recién más adelante (“unsupported operand type NoneType”). Si la función produce un valor, terminá con return.
  • Capturar Exception a ciegas: except Exception: pass esconde todos los errores, incluidos los bugs que necesitás ver. Capturá el error específico que esperás (except ValueError:) y dejá que el resto explote.
  • Modificar los argumentos recibidos: si tu función hace flujos.append(...) sobre la lista que le pasaron, el llamador ve su lista alterada sin saberlo. Trabajá sobre una copia (flujos = list(flujos)) o no mutes.
  • Validar tarde (o nunca): validar los inputs al inicio de la función (como hace valuacion_bono) da errores claros y cercanos a la causa; sin validación, el error aparece diez llamadas más adentro con un mensaje incomprensible.

# Definición de Funciones

Una función es un bloque de código reutilizable que recibe **parámetros** y devuelve un **resultado**.

```{pyodide-python}
#| label: funcion-basica
def valor_futuro(capital, tasa, periodos):
    """
    Calcula el valor futuro de una inversión.
    
    Parámetros:
    -----------
    capital : float — Monto inicial invertido
    tasa : float — Tasa de interés por período
    periodos : int — Número de períodos
    
    Retorna:
    --------
    float — Valor futuro
    """
    return capital * (1 + tasa) ** periodos

# Uso
vf = valor_futuro(100_000, 0.08, 10)
print(f"Valor futuro: ${vf:,.2f}")
```

## Recibir y devolver múltiples valores

En Python, una función puede **recibir varios parámetros** y también **devolver más de un resultado**.
Esto es útil en finanzas cuando, a partir de los mismos datos, queremos obtener más de un indicador.

```{pyodide-python}
#| label: multi-params-return
def resumen_inversion(capital, tasa, periodos):
    vf = capital * (1 + tasa) ** periodos
    interes_ganado = vf - capital
    rendimiento_total = interes_ganado / capital
    return vf, interes_ganado, rendimiento_total

# La función recibe 3 parámetros y devuelve 3 valores
vf, interes, rendimiento = resumen_inversion(100_000, 0.08, 3)

print(f"Valor futuro: ${vf:,.2f}")
print(f"Interés ganado: ${interes:,.2f}")
print(f"Rendimiento total: {rendimiento:.2%}")
```

Cuando devolvemos varios valores, Python los empaqueta en una tupla.
Luego podemos "desempaquetarlos" en variables separadas para trabajar con cada resultado de forma clara.

## Parámetros por Defecto

```{pyodide-python}
#| label: params-default
def valor_presente(flujo_futuro, tasa, periodos=1):
    """Calcula el valor presente. Por defecto, 1 período."""
    return flujo_futuro / (1 + tasa) ** periodos

# Con y sin el parámetro por defecto
vp1 = valor_presente(1000, 0.10)       # 1 período (default)
vp2 = valor_presente(1000, 0.10, 5)    # 5 períodos

print(f"VP a 1 año: ${vp1:,.2f}")
print(f"VP a 5 años: ${vp2:,.2f}")
```

## Argumentos Variables (`*args`)

Hasta ahora vimos funciones con una cantidad fija de parámetros.  
Pero en problemas financieros muchas veces no sabemos de antemano cuántos valores vamos a procesar (por ejemplo, una serie de flujos que puede tener 3, 10 o 30 períodos).

`*args` permite que una función reciba una **cantidad variable de argumentos posicionales**.
Dentro de la función, esos argumentos se agrupan en una **tupla**.

Esto nos da flexibilidad sin tener que escribir versiones distintas de la misma función.

```{pyodide-python}
#| label: args
def sumar_flujos(*flujos):
    """Suma una cantidad variable de flujos de fondos."""
    total = 0
    for f in flujos:
        total += f
    return total

# Podemos pasar cualquier cantidad de argumentos
total_1 = sumar_flujos(100, 200, 300)
total_2 = sumar_flujos(80, 80, 80, 80, 1080)

print(f"Total 3 flujos: ${total_1:,}")
print(f"Total 5 flujos: ${total_2:,}")

# Si ya tenemos una lista, usamos * para desempaquetar
serie = [-1000, 300, 400, 500]
print(f"Suma serie: ${sumar_flujos(*serie):,}")
```

Con esto:

- `sumar_flujos(100, 200, 300)` envía 3 argumentos,
- `sumar_flujos(80, 80, 80, 80, 1080)` envía 5,
- y `sumar_flujos(*serie)` toma una lista y la transforma en argumentos separados.

:::: {.callout-tip title="Cuándo usar *args"}
Usá `*args` cuando la función necesite aceptar una cantidad variable de datos del mismo tipo (flujos, retornos, precios, etc.).  
Si cada dato tiene un rol distinto y fijo (por ejemplo `capital`, `tasa`, `periodos`), conviene usar parámetros explícitos.

```{pyodide-python}
#| label: scope-basico
tasa_mercado = 0.05  # VARIABLE GLOBAL (Scope: Main)

def calcular_rendimiento(monto):
    # tasa_mercado es visible aquí porque es global
    return monto * tasa_mercado

def operacion_interna():
    variable_interna = 100  # VARIABLE LOCAL (Scope: Función)
    print(f"Dentro de la función: {variable_interna}")

print(f"Rendimiento calculado: {calcular_rendimiento(1000)}")
operacion_interna()

# Intentar acceder a variable_interna aquí daría un NameError
# print(variable_interna) 
```

## El concepto de "Shadowing" (Sombreado)

Si definimos una variable dentro de una función con el mismo nombre que una global, la versión local "sombra" a la global durante la ejecución de esa función.

```{pyodide-python}
#| label: scope-shadowing
ticker = "AAPL"

def cambiar_ticker_local():
    ticker = "GGAL"  # Esto crea una variable LOCAL, no cambia la global
    print(f"Dentro de la función: {ticker}")

cambiar_ticker_local()
print(f"Fuera de la función (Global): {ticker}")
```

## ¿Por qué evitar las variables globales?

En el desarrollo de software financiero, la **pureza** de las funciones es fundamental. Una función ideal es aquella que, para los mismos parámetros, siempre devuelve el mismo resultado sin depender de "estados externos".

```{pyodide-python}
#| label: scope-mala-practica
# MALA PRÁCTICA (Dependencia global)
tasa = 0.10
def calcular_interes_malo(capital):
    return capital * tasa

# BUENA PRÁCTICA (Parámetros explícitos)
def calcular_interes_bueno(capital, tasa_activa):
    return capital * tasa_activa

print(f"Malo: {calcular_interes_malo(100)}")
print(f"Bueno: {calcular_interes_bueno(100, 0.12)}")
```

::: {.callout-important title="Regla de Oro"}
Siempre que necesites un dato dentro de una función, **pásalo como parámetro**. Evita depender de variables definidas en el "main" para que tu código sea modular y fácil de testear.
:::

## ¿Qué recibe una función cuando le pasás una lista?

Cerremos el círculo con el concepto de *aliasing* del Capítulo 2 ("copiar no es lo mismo que apuntar"), porque tiene una consecuencia directa sobre las funciones. Cuando llamás `mi_funcion(cartera)`, la función **no recibe una copia** de la cartera: recibe **otra etiqueta al mismo objeto**. Con parámetros inmutables (números, strings) esto es invisible — no se pueden modificar. Pero con una **lista o diccionario**, si la función lo muta, *el llamador ve el cambio*:

```{pyodide-python}
#| label: mutar-argumentos
def aplicar_comision(flujos):
    """Descuenta 1% de comisión a cada flujo... modificando la lista recibida."""
    for i in range(len(flujos)):
        flujos[i] = flujos[i] * 0.99
    return flujos

mis_flujos = [1000.0, 1000.0, 1000.0]
flujos_netos = aplicar_comision(mis_flujos)

print(f"Flujos netos:      {flujos_netos}")
print(f"¿Y mis originales? {mis_flujos}   ← ¡también cambiaron!")
```

La función "devolvió" los flujos netos, pero de paso **destruyó los originales** — `mis_flujos` y el parámetro `flujos` eran el mismo objeto. En un análisis real esto es venenoso: valuás la cartera dos veces y da distinto, porque la primera pasada la modificó. Hay dos diseños correctos, y ambos empiezan igual — **no mutar lo que te prestaron**:

```{pyodide-python}
#| label: no-mutar-argumentos
def aplicar_comision_bien(flujos):
    """Versión pura: trabaja sobre una copia y devuelve una lista nueva."""
    netos = []
    for f in flujos:
        netos.append(f * 0.99)
    return netos

mis_flujos = [1000.0, 1000.0, 1000.0]
flujos_netos = aplicar_comision_bien(mis_flujos)

print(f"Flujos netos:      {flujos_netos}")
print(f"Originales intactos: {mis_flujos}")
```

::: {.callout-tip title="La convención del oficio"}
Una función debería **recibir datos, devolver resultados y no tocar nada más** — ni globales (la sección anterior) ni los objetos que le pasaron (esta). A las funciones que cumplen esto se las llama *puras*, y son las más fáciles de testear, reutilizar y razonar. Todas las funciones de la librería que construimos al final del capítulo son puras.
:::

# Manejo de Errores: `try` / `except`

En el mundo real, los datos financieros casi nunca llegan "perfectos": pueden venir incompletos, en formato incorrecto o fuera de rango.
El manejo de excepciones con `try` / `except` permite que el programa sea **robusto**, evitando que se rompa ante errores esperables.

## ¿Qué es una excepción?

Una **excepción** es un error que ocurre durante la ejecución del programa (runtime), por ejemplo:

- dividir por cero (`ZeroDivisionError`),
- convertir texto a número cuando no se puede (`ValueError`),
- acceder a una clave inexistente en un diccionario (`KeyError`),
- o intentar usar un tipo de dato incorrecto (`TypeError`).

Si no capturamos la excepción, el programa se detiene **e imprime un traceback** — el "informe forense" del error. Saber leerlo es probablemente la habilidad que más tiempo te va a ahorrar en toda tu carrera, así que detengámonos un minuto.

::: {.callout-tip title="Cómo leer un traceback (la habilidad subvalorada)"}
Un traceback típico luce así:

```
Traceback (most recent call last):
  File "analisis.py", line 42, in <module>
    resultado = valuar_cartera(posiciones)
  File "analisis.py", line 17, in valuar_cartera
    total += valuacion_bono(bono, tasa)
  File "finanzas_basicas.py", line 8, in valuacion_bono
    return cupon / (1 + tasa) ** t
ZeroDivisionError: division by zero
```

La receta para leerlo:

1. **Empezá por la última línea**: ahí está el *tipo* de error (`ZeroDivisionError`) y el *mensaje* (`division by zero`). Es el "qué pasó".
2. **Subí una línea**: es el lugar exacto donde explotó (`finanzas_basicas.py`, línea 8). Es el "dónde".
3. **El resto, de abajo hacia arriba, es la cadena de llamadas**: quién llamó a quién hasta llegar ahí. El "cómo llegamos". Ojo: la línea que explotó no siempre es la culpable — acá el bug probablemente esté en quien pasó `tasa = -1`, no en la fórmula.

El error de principiante es leer solo la primera línea (que es la *menos* informativa) o, peor, no leer nada y adivinar. El traceback te está diciendo exactamente qué, dónde y cómo — gratis.
:::

Con `try` / `except`, en cambio, podemos capturar el error y decidir cómo responder sin que el programa muera.

## Flujo de `try` / `except`

La estructura general es:

```python
try:
    # código que puede fallar
except TipoDeError:
    # qué hacer si ocurre ese error
```

La idea clave es separar:

- **camino normal** (cálculo esperado),
- de **camino de error** (qué hacemos cuando algo falla).

## Ejemplo base: validación y captura en VPN

```{pyodide-python}
#| label: try-except
def calcular_vpn(flujos, tasa):
    """Calcula el VPN de una serie de flujos."""
    if len(flujos) == 0:
        raise ValueError("La lista de flujos no puede estar vacía")

    vpn = 0
    for t, cf in enumerate(flujos):
        vpn += cf / (1 + tasa) ** t
    return vpn

# Caso normal
print(f"VPN correcto: {calcular_vpn([-1000, 400, 400, 400], 0.10):.2f}")

# Caso con error controlado (lista vacía)
try:
    resultado = calcular_vpn([], 0.10)
except ValueError as e:
    print(f"Error capturado: {e}")
```

## Capturar múltiples excepciones

Podemos manejar cada tipo de error de forma distinta:

```{pyodide-python}
#| label: try-except-multiple
def ratio_cobertura(ebit, intereses):
    return ebit / intereses

try:
    print(ratio_cobertura(500, 0))  # podría fallar por división por cero
except ZeroDivisionError:
    print("Error: intereses no puede ser 0")
except TypeError:
    print("Error: ebit e intereses deben ser numéricos")
```

Esto es útil porque no todos los errores deben tener el mismo mensaje o tratamiento.

## Uso de `else` y `finally`

Además de `except`, Python ofrece dos bloques muy útiles:

- `else`: se ejecuta si **no** hubo excepción en `try`.
- `finally`: se ejecuta **siempre**, haya error o no.

```{pyodide-python}
#| label: try-except-else-finally
def parse_tasa(texto):
    return float(texto)

entrada = "0.12"

try:
    tasa = parse_tasa(entrada)
except ValueError:
    print("No se pudo convertir la tasa a número")
else:
    print(f"Tasa válida: {tasa:.2%}")
finally:
    print("Fin de la validación")
```

En análisis financiero real, `finally` suele usarse para cerrar archivos, conexiones o liberar recursos.

## `raise`: generar errores de negocio explícitos

No solo capturamos errores: también podemos **lanzarlos** cuando una regla financiera no se cumple.

```{pyodide-python}
#| label: try-except-raise
def cuota_francesa(capital, tasa, periodos):
    if capital <= 0:
        raise ValueError("El capital debe ser positivo")
    if tasa <= 0:
        raise ValueError("La tasa debe ser positiva")
    if periodos <= 0:
        raise ValueError("Los periodos deben ser mayores a 0")
    return capital * (tasa * (1 + tasa) ** periodos) / ((1 + tasa) ** periodos - 1)

try:
    cuota = cuota_francesa(100000, 0.03, 24)
    print(f"Cuota: ${cuota:,.2f}")
except ValueError as e:
    print(f"Dato inválido: {e}")
```

## Buenas prácticas en `try` / `except`

1. Capturar errores **específicos** (`ValueError`, `TypeError`, etc.), no usar `except:` genérico salvo casos muy controlados.
2. Mantener el bloque `try` **pequeño** (solo las líneas que pueden fallar).
3. Dar mensajes claros para quien usa el programa.
4. Validar supuestos de negocio con `raise` (tasas, plazos, signos de flujos).
5. No ocultar errores silenciosamente (`pass`) si eso dificulta detectar problemas.

:::: {.callout-important title="Idea clave"}
`try` / `except` no reemplaza una buena lógica: la complementa.  
Primero validamos reglas financieras, luego capturamos errores inevitables del mundo real.
::::

# Módulos y librerías en Python

Cuando un programa crece, no conviene dejar todo en un solo archivo. Python permite **organizar el código en módulos** para reutilizar funciones, mantener orden y facilitar el testing.

## ¿Para qué sirve un módulo?

Un **módulo** es, en la práctica, un archivo `.py` con funciones, variables o clases.

Nos sirve para:

- separar responsabilidades (por ejemplo, valuación de bonos en un archivo y conversión de tasas en otro),
- reutilizar lógica en distintos scripts o notebooks,
- evitar duplicación de código (principio DRY),
- y mejorar mantenimiento y legibilidad.

## Diferencia entre módulo y librería

- **Módulo**: un archivo Python individual, por ejemplo `finanzas_basicas.py`.
- **Librería**: un conjunto de módulos relacionados que resuelven un dominio o problema.  
  Ejemplos: `numpy`, `pandas`, `matplotlib`.

En cursos introductorios, a veces se dice "librería" para referirse a un solo archivo propio. Técnicamente, ese archivo es un **módulo**, aunque puede ser el primer paso para construir una librería más completa.

## Formas de importar: `import`, `from`, `as`

```{pyodide-python}
# 1) import modulo
import math
print(math.sqrt(16))  # accedemos con prefijo math.

# 2) import modulo as alias
import math as m
print(m.pi)  # mismo módulo, nombre corto

# 3) from modulo import nombre
from math import sqrt
print(sqrt(25))  # usamos sqrt directamente

# 4) from modulo import nombre as alias
from math import factorial as fact
print(fact(5))
```

:::: {.callout-note title="Buena práctica"}
En general, preferí `import modulo` o `import modulo as alias` porque hacen explícito de dónde viene cada función (`modulo.funcion`).  
`from modulo import *` no se recomienda en producción porque puede sobrescribir nombres y volver ambiguo el código.
::::

# Problemática Financiera: Librería `finanzas_basicas.py`

Hora de cosechar lo sembrado. En los dos capítulos anteriores resolviste problemas financieros reales —interés compuesto, conversión de tasas, valuación de bonos, TIR— pero cada solución quedó atrapada en su ejemplo. Vamos a **rescatar esa lógica y empaquetarla en una librería reutilizable**: el conjunto de funciones que vas a poder importar en cualquier análisis futuro. En un entorno real, este código viviría en un archivo `finanzas_basicas.py` y se importaría con `from finanzas_basicas import valuacion_bono, tir`.

## Funciones de la Librería

```{pyodide-python}
#| label: libreria
# === finanzas_basicas.py ===
# En un proyecto real, este bloque viviría en su propio archivo .py
# y lo importarías con: from finanzas_basicas import valor_futuro, ...

def valor_futuro(capital, tasa, periodos):
    """Calcula VF = C * (1 + r)^n."""
    if tasa < -1:
        raise ValueError("La tasa no puede ser menor a -100%")
    return capital * (1 + tasa) ** periodos


def valor_presente_neto(flujos, tasa):
    """Calcula el VPN de una serie de flujos (el flujo 0 no se descuenta)."""
    if not flujos:
        raise ValueError("Lista de flujos vacía")

    vpn = 0
    for t, cf in enumerate(flujos):
        vpn += cf / (1 + tasa) ** t
    return vpn


def conversion_tasas(tna, capitalizaciones=12):
    """Convierte una TNA con n capitalizaciones anuales a TEA."""
    if capitalizaciones <= 0:
        raise ValueError("Las capitalizaciones deben ser positivas")
    return (1 + tna / capitalizaciones) ** capitalizaciones - 1


def valuacion_bono(valor_nominal, tasa_cupon, tasa_descuento, anios):
    """Precio de un bono bullet: cupones fijos + nominal al vencimiento.

    Es la lógica del Capítulo 2, ahora encapsulada y validada.
    """
    if tasa_cupon < 0 or anios <= 0:
        raise ValueError("Cupón no negativo y plazo positivo")

    cupon = valor_nominal * tasa_cupon
    precio = 0
    for t in range(1, anios + 1):
        flujo = cupon + (valor_nominal if t == anios else 0)
        precio += flujo / (1 + tasa_descuento) ** t
    return precio


def tir(valor_nominal, tasa_cupon, anios, precio_mercado, paso=0.0001):
    """TIR de un bono bullet por búsqueda incremental (Capítulo 2)."""
    if precio_mercado <= 0:
        raise ValueError("El precio debe ser positivo")

    tasa = 0.0
    while valuacion_bono(valor_nominal, tasa_cupon, tasa, anios) > precio_mercado:
        tasa += paso
        if tasa > 5:   # techo de seguridad: 500% anual
            raise ValueError("No se encontró TIR razonable: revisar inputs")
    return tasa
```

Fijate el detalle de diseño en `tir()`: **reutiliza `valuacion_bono()`** en lugar de repetir el bucle de descuento. Las funciones de una librería se apoyan unas en otras — si mañana mejorás la valuación, la TIR mejora gratis. Notá también el "techo de seguridad": una función de librería no puede colgarse en un bucle infinito porque alguien le pasó un precio absurdo; falla rápido y con un mensaje claro.

## Usando la Librería

```{pyodide-python}
#| label: uso-libreria
# === Uso de las funciones ===

# 1. Valor futuro de una colocación
vf = valor_futuro(100_000, 0.08, 3)
print(f"Valor futuro: ${vf:,.2f}")

# 2. VPN de un proyecto de inversión
flujos = [-1000, 400, 400, 400]
vpn = valor_presente_neto(flujos, 0.10)
print(f"VPN: ${vpn:,.2f}")

# 3. Conversión de tasas: TNA 48% con capitalización mensual → TEA
tea = conversion_tasas(0.48, 12)
print(f"TNA 48% mensual → TEA: {tea:.2%}")

# 4. Valuación del bono del Capítulo 2, ahora en una línea
precio = valuacion_bono(1000, 0.08, 0.10, 5)
print(f"Precio del bono: ${precio:,.2f}")

# 5. Y su TIR comprándolo a $950
rendimiento = tir(1000, 0.08, 5, 950)
print(f"TIR al precio de $950: {rendimiento:.2%}")
```

Compará el punto 4 con las ~10 líneas de bucle que necesitaste en el Capítulo 2: la misma lógica, pero ahora **valuar un bono es una línea** — y con validación de inputs incluida. Ese salto de "código que escribo cada vez" a "herramienta que invoco" es exactamente lo que este capítulo vino a enseñar. En el próximo capítulo estas funciones van a dar su paso final: convertirse en *métodos* de una clase `Bono`.

# Principio DRY: Don't Repeat Yourself
El principio **DRY** (*Don't Repeat Yourself*) propone evitar duplicar la misma lógica en distintos lugares del código.
Cuando repetimos fórmulas o bloques manualmente, aumentamos el riesgo de inconsistencias: si cambia un supuesto (por ejemplo, la tasa o la frecuencia), debemos corregir múltiples líneas y es fácil olvidar alguna.

Aplicar DRY en finanzas significa **encapsular cálculos recurrentes en funciones** (por ejemplo, `valuacion_bono()` o `valor_presente_neto()`) para tener:

- **menos errores** de mantenimiento,
- **mayor claridad** del modelo,
- **reutilización** en distintos ejercicios o casos,
- y **validaciones centralizadas** en un solo lugar.

::: {.callout-tip title="DRY en la Práctica"}
Antes de copiar y pegar código, preguntate: *¿puedo hacer una función?*

**Sin DRY** (malo):
```python
precio_a = 80/(1.1) + 80/(1.1**2) + 1080/(1.1**3)
precio_b = 60/(1.08) + 60/(1.08**2) + 1060/(1.08**3)
```

**Con DRY** (bueno):
```python
precio_a = valuacion_bono(1000, 0.08, 0.10, 3)
precio_b = valuacion_bono(1000, 0.06, 0.08, 3)
```
:::

# Errores comunes

::: {.callout-warning title="Trampas frecuentes"}
- **Argumento por defecto mutable**: `def agregar(flujo, lista=[])` comparte la MISMA lista entre todas las llamadas — los flujos de un bono aparecen en otro. El idioma correcto: `def agregar(flujo, lista=None)` y crear la lista adentro (`if lista is None: lista = []`).
- **Olvidar el `return`**: una función que calcula pero no retorna devuelve `None` silenciosamente; el error explota recién más adelante ("unsupported operand type NoneType"). Si la función produce un valor, terminá con `return`.
- **Capturar `Exception` a ciegas**: `except Exception: pass` esconde *todos* los errores, incluidos los bugs que necesitás ver. Capturá el error específico que esperás (`except ValueError:`) y dejá que el resto explote.
- **Modificar los argumentos recibidos**: si tu función hace `flujos.append(...)` sobre la lista que le pasaron, el llamador ve su lista alterada sin saberlo. Trabajá sobre una copia (`flujos = list(flujos)`) o no mutes.
- **Validar tarde (o nunca)**: validar los inputs al inicio de la función (como hace `valuacion_bono`) da errores claros y cercanos a la causa; sin validación, el error aparece diez llamadas más adentro con un mensaje incomprensible.
:::
